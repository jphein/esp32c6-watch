UI Overhaul · Interaction Design

Every tap should announce itself.

Today exactly one screen acknowledges a press. This is the standard for the rest of the watch: a bold, one-frame pressed state on every interactive element — the only feedback channel we have, because the board has no haptic motor and audio-click is offline. Press the mockups below — they swap on :active exactly like the recipes specify.

1Rest → Pressed → Disabled. Every touchable element binds its fill/border/glyph to TouchArea.pressed — a bold, unmistakable swap while the finger is down.
2Hard swap, no tween. One direct pressed binding = one already-scheduled full-frame repaint. No animate on press — at 6–11 fps a tween is wasted frames.
3Tokens only, all four schemes. Pressed = accent-bg fill + accent edge, or invert to on-accent. No hex, no per-scheme code.
410×502 CO5300 AMOLED 90–170 ms full-frame render ~100 ms perceived-instant target 0 haptic motors Slint 1.17 · sw renderer · no_std
The constraint that shapes everything

We get one frame. Make it count.

A full-frame repaint takes 90–170 ms and there is no partial rendering (reverted, #18). So the pressed state can't tween in — it lands as a single frame ~one render after touch, right at the edge of the ~100 ms "instant" threshold. The answer isn't a subtle 12% Material overlay (invisible here) — it's a large, high-contrast delta that reads unambiguously even as one late frame.

No new colors needed

The palette already ships the feedback tokens.

These four tokens (from theme.slint) carry the whole standard. The palette contract guarantees accent stays bright enough that on-accent reads on it in all four schemes — so the invert recipe needs zero per-scheme logic.

TokenPalette roleFeedback job
accent-bgtinted fill behind a primary/accent actionthe pressed fill for tiles, WLED, icon halos, segments

on-accentnear-black ink on a bright fillthe inverted text/glyph when a control fills with accent
warn / warn-bgdanger fill + tintthe same recipe for destructive actions (reboot)
Guardrails

What not to do at 6–11 fps.

The render budget rules out most of the "delight" a phone UI leans on. Discipline here is the design.

No animate on pressA tween needs a repaint per step; at our framerate that's 0–1 wasted frames plus extra repaints on fast taps. Bind directly to pressed. (Retire climate's animate 120ms.)
No continuous motionNo spinners, breathing glows, shimmers. Each frame is a full 410×502 repaint — motion stutters and pins the CPU.
No has-hover stylingA touch panel never hovers. Hover states are dead code here.
No shadows / blur / motion-gradients on deviceThe sw renderer can't afford them and near-black gradients band. Flat fills + hairline borders.
No subtle overlaysA 12% Material state layer is invisible at our contrast + framerate. Go bold: fill swaps and inversions.
Don't shrink hit targets≥44px floor. The pressed halo lives inside the existing target — never trades away tappable area.
Implementation order

Phased rollout for Luna.

Each phase is independently shippable and on-glass verifiable. Because feedback is a per-element visual swap, phases don't collide.

Phase 0Foundation. Build ui/slint/controls.slint — shared PressTile · IconButton · Stepper · PillButton · Seg · SliderControl implementing each recipe once. Add type/spacing tokens. This makes it a system, not 40 inline ternaries.
Phase 1Highest-traffic surfaces. Launcher tiles, radio dots, back-chevron, page dots — touched every session, every screen. Biggest perceived win.
Phase 2App controls. WLED grid, mic-gain steppers, reboot, brightness knob, theme swatches, hunt "next".
Phase 3Round-trip-lag killers. Voice PTT local pressed state (react before the loop returns) and climate list rows — worst perceived lag today.
Phase 4Align the reference. Migrate climate.slint onto the shared components, drop its press animates. Whole UI now consistent.
Phase 5Polish. Typography/spacing sweep, AOD pixel-shift, corner-safe re-audit, optional fb-app pressed cells.
